# 浏览器平台游戏生产经验手册

**适用对象：** Godot Web 平台跳跃游戏
**目标：** 使用模板内已经运行过的代码、素材和测试作为下一款游戏的生产起点。

## 1. 默认先做“可调的游戏”，再做“正确的游戏”

游戏手感很难仅靠自然语言一次描述准确。速度、加速度、摩擦、重力、跳跃力度、土狼时间、跳跃缓冲、敌人速度、关卡时间和镜头平滑度，应在首个可玩版本中就进入统一参数表，并由游戏内面板实时调节。用户可以直接操作和比较，不需要反复描述“再快一点”或“跳得自然一些”。

模板已经提供 `TuningStore` 和 `TuningPanel`。角色、敌人、镜头和关卡计时从参数服务读取数值；调整范围和步进由面板集中维护。确定手感后，再把验证过的值更新为默认值。

| 默认开发能力 | 模板实现 | Release 行为 |
|---|---|---|
| 参数调节 | `TuningStore` + `TuningPanel` | 默认不实例化 |
| 检查点重生 | `game.gd` 中的 checkpoint 与 respawn 流程 | 正常启用 |
| 状态截图 | `test/debug_capture.gd` | 不进入游戏主流程 |
| 存档清理 | 独立调试操作按需增加 | 默认不暴露 |

> Debug 工具只属于开发构建。Checkpoint 与正式发布使用 release 构建，不提供调参入口。

模板暂未内置关卡选择器。需要多关卡时，新增 `LevelDefinition` 数据，至少包含场景路径、显示名、默认出生点、可用检查点和解锁条件，不要把所有关卡继续堆进一个脚本。

## 2. 把生成式美术作为资产系统

生成图片的目标不是单张漂亮背景，而是建立统一视觉语言。开始生成前先固定角色比例、轮廓、色板、光照、描边、视角、地平线和目标分辨率，再让背景、角色、砖块与前景共享这些约束。

### 2.1 分层背景和视差

模板在 `world_art.gd` 和 `assets/template/generated/` 中提供远、中、近三层可运行参考。远景承担天空和大形状，中景承担山丘或建筑，近景承担植被与遮挡。每层单独输出、水平可平铺，并避免在接缝处放置独特主体。

| 层级 | 模板素材 | 参考滚动速度 |
|---|---|---:|
| 远景 | `sky_far.webp` | `0.04` |
| 中景 | `hills_mid.webp` | `0.18` |
| 近景 | `foliage_near.webp` | `0.42` |

近景透明元素不应大量重叠。Web/WASM 渲染时，过度透明填充会快速消耗帧预算。所有素材按实际显示尺寸缩放并保存为 WebP，不保留没有运行价值的超大原图。

### 2.2 角色动作序列帧

静态图负责定妆，视频负责动作。先用生图生成并确认唯一的角色参考图；跑、走、跳、攻击、受击和死亡等连续动作，必须以该参考图作为输入，分别生成短视频，再从视频抽帧。不要让生图模型逐张生成动作姿势，也不要直接生成 sprite sheet；独立图片没有共同时间轴，角色结构、服装细节、比例和镜头会在帧间漂移。只有用户明确选择逐帧跳变的风格时才允许例外。

当 Agent 同时拥有生图和视频生成工具时，连续动作必须选择视频生成工具。调用生图工具得到多张动作帧属于流程失败，不能靠后续裁切和对齐掩盖，也不能作为最终动画交付；必须以角色参考图重新生成动作视频。

每个动作使用单独视频。视频必须固定侧视机位、固定画幅和角色比例，角色原地完成动作，背景使用纯绿色；禁止运镜、缩放、剪辑、文字、额外人物和场景切换。原始视频和抽出的 PNG 放在 Godot 项目目录外，只有处理后的运行时文件进入 `assets/template/`。根据当前游戏实际内容自行设计有语义的一级目录，只创建这个游戏需要的分组，不使用预设分组列表；一级目录会自动成为 Assets 面板分组，内部可继续使用多级目录且不会拆出额外分组。项目资产不得放入 `assets/template/`。

1. 确认唯一静态角色参考图。
2. 以参考图生成一个动作对应的一段连续视频。
3. 选择视频中动作连贯的区间，删除预备段和收尾段。
4. 使用 `extract_video_frames.py` 按固定帧率抽帧。
5. 去除背景，保留柔和 Alpha 边缘。
6. 对该动作的所有帧使用共同裁剪区域、角色中心和脚底基线。
7. 缩放到游戏实际画布并导出 WebP。
8. 在 GDScript 中使用静态 `preload()` 列出帧。
9. 在实际播放和 Debug 截图中检查连续性、透明度、翻转、锚点和真实尺寸。

| 动作 | 建议形式 | 关键要求 |
|---|---|---|
| Idle | 4–8 帧循环 | 呼吸幅度小，脚底稳定 |
| Run | 8–16 帧循环 | 首尾速度连续，身体不漂移 |
| Jump | 起跳、上升、下落、落地分段 | 依据垂直速度选帧 |
| Attack | 6–12 帧一次性播放 | 命中帧与碰撞窗口一致 |
| Hit | 3–6 帧短反馈 | 轮廓清晰 |
| Death | 8–16 帧一次性播放 | 完成后进入重生流程 |

模板已内嵌跑步序列帧以及视频抽帧、去背景和帧对齐工具。处理新动作时只更换视频、动作区间、帧率、输入输出目录、前缀和目标画布，不复制一套新的固定路径脚本。

## 3. 测试优先使用引擎 Debug

画面、碰撞、状态机和 UI 的高频迭代先由 Godot 验证。浏览器端到端测试只负责 Web/WASM、浏览器存储和发布壳等浏览器特有行为。

| 层次 | 验证目标 | 模板入口 |
|---|---|---|
| 资源导入 | 图片可读取、导入配置正常 | `godot --headless --path . --import` |
| 脚本与场景 | 场景、世界、移动、调参可运行 | `test/smoke.gd` |
| 视觉状态 | 真实渲染、透明度、层级、动画、调参 UI | `test/debug_capture.tscn` |
| 导出完整性 | PCK 中不存在漏打资源 | `test/exported_pack_boot.gd` |
| 浏览器行为 | WASM 启动、浏览器存储、发布资源加载 | 少量浏览器集成测试 |

截图测试应直接把游戏推进到目标状态。模板会截取标题页、模拟移动和跳跃后的真实玩法，以及调参面板，而不是要求人工跑完整关卡。为新机制增加截图时，同时加入状态断言，避免只有图片没有通过条件。

## 4. Web 发布区分开发导出与生产分发

开发预览由 Sandbox 直接提供 `dist/index.wasm` 和 `dist/index.pck`。普通 checkpoint 会运行模板内的 artifacts hook，必要时重新导出游戏并更新轻量 `site/` 发布壳。存 checkpoint 是产出发布物的唯一途径，没有手动等价命令。

不要手改 `dist/` 或 `site/`，也不要在 Sandbox 内运行 `pnpm build`。发布与回滚的完整行为以模板 `README.md` 的 Publishing 章节为准。

## 5. 模板默认组成

| 模块 | 已内嵌内容 |
|---|---|
| Gameplay tuning | 参数、实时面板、保存/重置、Debug 门控 |
| Platformer core | 加速、摩擦、重力、可变跳跃、土狼时间、输入缓冲、踩踏 |
| Level reference | 长关卡、平台、坑、管道、问题块、金币、敌人、检查点、终点 |
| Art pipeline | 三层视差、角色参考素材、跑步帧、去背景和对齐脚本 |
| Input | 键盘、触控拖动、触控跳跃 |
| Persistence | 版本化最高分与独立调参数据 |
| Test harness | Headless smoke、Debug 截图、PCK 启动检查 |
| Web publish | WASM/PCK 存储映射与轻量发布壳 |

## 6. 发布前检查清单

模板 `README.md` 的 **Definition of done: complete game delivery** 是唯一完成标准。除非用户明确排除某一项，否则 Agent 必须完成其中每一项并给出可观察的验收证据；仍有缺项时只能报告“进行中”，不能把可启动的样例或单个机制描述成完整游戏。

发布前还需确认使用 release 导出，测试截图和中间素材未进入包体，单个媒体文件低于项目限制，PCK 包含全部静态依赖，`site/` 由最新导出重新生成，并通过导出包启动测试和真实 Web 预览。
